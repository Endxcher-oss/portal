# 设计说明

## 为什么一个端口一条隧道

Cloudflare 的快速隧道是 L7 反向代理，不是 L4 端口转发：它只认一个上游地址，公网侧端口固定由 Cloudflare 边缘决定。想让 `a.example.com` 和 `b.example.com` 同时指向本机两个端口，只能：

1. 每个端口一条隧道，各自的随机域名（本项目采用）；
2. 一条命名隧道按 hostname 分流——需要自有域名并把 zone 交给 Cloudflare；
3. 一条隧道按路径前缀分流——需要被发布的应用配合（绝对路径资源会碎）。

选 1 的原因是零配置、不要求域名，而且每个端口天然落在不同源（origin）上：cookie 按域名隔离，多个端口可以在同一个浏览器里同时登录、同时使用，这是路径前缀方案做不到的。

## token 交换

链接形如 `https://<随机域名>/path?token=<随机串>`。token 用 `secrets.token_urlsafe(24)` 生成（约 144 bit），不做密码强度限制，因为它不是给人记的。

请求带 `token` 时：校验 → 下发 cookie → 303 到去掉 `token` 的同一路径。这样 token 不会留在浏览器历史、截图、Referer 和 Cloudflare 的访问日志里；之后所有请求都只带 cookie。

cookie 值 `"<过期时间戳>.<HMAC-SHA256>"`，密钥是进程启动时随机的 32 字节——重启即全部失效，不需要额外的吊销逻辑。只有请求带 `cf-visitor`（即经过 Cloudflare）时才加 `Secure`，否则本机直连 http 收不到 cookie。

## 透明转发

每个目标一个独立的 `asyncio` 服务，监听 `127.0.0.1:0`（随机端口），由对应的 cloudflared 指过来。转发时：

- 保留原始 `Host`，让后端应用看到它以为的域名；
- 非 WebSocket 请求补 `Connection: close` 并逐跳剥掉 `Connection`/`Keep-Alive`，避免连接复用把状态搅乱；
- 请求体支持 `Content-Length` 和 `chunked`；
- `Upgrade: websocket` 且上游回 101 时，双向泵字节，直到任一侧断开。

`/_portal/` 是保留路径，用来渲染索引页；索引页里的每个链接都自带该域名的 token，所以点进去就能完成交换。

## 后端挂掉时返回 503 而不是 502

Cloudflare 会把源站返回的 502 替换成它自己的错误页，用户看不到我们写的原因。503 会原样透传，所以连接本地端口失败时回 503 并说明是哪个端口。

## 失败处理

隧道是并发建立的，某个端口失败不影响其它端口：失败的目标会关掉自己的代理，在启动摘要里记为「隧道未建立」，进程继续服务剩下的端口；如果一个都没起来，进程退出并返回非零。

## 已知取舍

- 域名随机且每次重启变化，适合临时分享，不适合固定入口。
- 不做 `Host` 改写，所以只信任 loopback `Host` 的应用（DSH）不能直接发布。
- 不校验 `Origin`：cookie 已经保证只有拿到链接的人能用，且 `SameSite=Lax` 挡住了跨站表单提交。
